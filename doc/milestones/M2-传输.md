## 核心设计:内容寻址 + 不信任客户端

对象 key 是 `blobs/{sha[:2]}/{sha}`,与文件名/归属彻底解耦。同一份内容全站物理只存一份,配额却按**逻辑大小**记——两个用户存同一文件各扣各的额度,防"传热门资源白嫖存储"。

hash 是客户端算的,**不可信**。信任模型分两级:
- `blobs.verified = false`:completeUpload 后的初始态。此时文件对上传者本人可见可用(乐观),但**秒传只认 verified 的 blob**——否则攻击者可以谎报热门文件的 hash 抢占 key,让后来者"秒传"到假内容。
- verify_hash 任务异步流式重算整个对象的 SHA-256:一致 → 标 verified,此后同 hash 全部秒传;不一致 → **全链回收**:删 MinIO 对象、删所有引用节点(PurgeSubtree)、退配额、删 blob 行、把关联上传会话标 failed(前端能看到"服务端校验失败")。

## 上传流程(service/upload.go)

1. **initUpload(parentId, name, sha256, size)**:校验 sha 格式/大小/配额/父目录,`cleanName` 解重名。查 blob:已存在且 verified → 事务内建节点 + `ref_count+1` + 加配额,返回 `instant: true`,上传结束;否则开 S3 multipart 会话,预签所有分片的 PUT URL 返回。
2. **浏览器直传**:每片一个预签名 URL(1 小时,绑定 key+uploadId+partNumber,拿到也只能写那一片),不经过 Go。
3. **uploadSession(id)**(断点续传入口):`ListObjectParts` 是**唯一事实源**——服务端不记"哪些片传完了",MinIO 说了算。返回已完成分片号 + 缺失分片的新预签名。
4. **completeUpload(sessionId, etags)**:客户端没报的 etag 从 ListParts 补齐(见踩坑 1),`CompleteMultipartUpload` 合并;然后单事务:UpsertBlob(pending verify)→ 建节点 → ref_count+1 → 加配额 → 会话标 verifying;提交后投递 verify_hash 任务。
5. 并发同 hash 上传:`UpsertBlob ON CONFLICT (sha256) DO UPDATE … RETURNING` 收敛到同一行,大小不一致直接拒绝。

会话有配套治理:单用户并发 session 上限 20(防恶意开会话耗 multipart 资源),48 小时过期,worker 每小时 AbortMultipart + 标 aborted 清理。

## 双 MinIO client(objstore/minio.go)

自部署 MinIO 最常见的坑在设计期就定死了:服务端可达地址和浏览器可达地址往往不同(容器网 vs 公网域名)。所以初始化两个 client——`internal` 做桶操作/校验读取,`public` 只用来生成预签名 URL(`GOPAN_S3_PUBLIC_ENDPOINT`)。分片 PUT 预签名用的是 minio-go Core API:`Presign("PUT", …, url.Values{uploadId, partNumber})`。

下载用 `response-content-disposition` 查询参数控制保存文件名(对象 key 是 hash,没有原名),预签名 GET 15 分钟、即查即用。

## worker 池(worker/worker.go)

单进程内嵌,不引消息队列。任务持久化在 tasks 表,`(kind, blob_id)` 唯一:

- **ClaimTask**:`FOR UPDATE SKIP LOCKED` 抢占,多 worker 不互踩;`running` 超 5 分钟无更新视为宿主死亡,可被重新认领——重启自动恢复。
- **EnqueueTask**:幂等,且 `ON CONFLICT … DO UPDATE SET status='pending' WHERE status='failed'`——失败过的任务同 hash 再次上传时能重新入队(见踩坑 3)。
- 唤醒:带缓冲 channel 即时唤醒 + 30 秒兜底轮询;失败重试 3 次后进终态 failed。
- **blob GC**:`ref_count = 0` 且 `deref_at` 过 24 小时宽限的 blob,删对象删行。宽限期防"刚删就又秒传"的抖动——重新引用时 `deref_at` 清空。

## 前端自研上传器(uploader/manager.ts,598 行)

选择自研而非 tus/Uppy:协议是自己的(GraphQL init/complete + S3 预签名 PUT),引一个框架再适配反而更多代码。

- **hash 阶段**:hash-wasm 在 Web Worker 里 `File.slice` 8MB 流式喂,恒定内存,主线程不卡,有进度。
- **并发模型**:全局同时 2 个文件,每文件 3 个分片并行。分片用 XMLHttpRequest(`upload.onprogress` 拿字节级进度;fetch 拿不到上传进度)。
- **状态机**(stores/uploads.ts):`queued → hashing → initiating → uploading → completing → done`,instant 从 initiating 直达 done;任何非终态可 → paused / failed / canceled。暂停/取消 = `xhr.abort()`,与真实失败靠 InterruptedError 区分。
- **重试**:任务级 3 次指数退避;分片级 3 次,403(预签名过期)时经 uploadSession 单飞刷新拿新签名重试该片。QUOTA_EXCEEDED 等致命码直接 failed 不重试。
- **断点续传**:`sessionId + 文件指纹(名字/大小/mtime/sha)` 存 localStorage;恢复时重新选文件 → 先 hash 校验与记录一致 → uploadSession 只传缺失分片。
- **速度**:3 秒滑动窗口采样,已完成分片字节 + 进行中分片 loaded 合计。

## 踩坑记录

1. **浏览器读不到分片响应的 ETag**:S3 CompleteMultipart 需要每片 etag,但跨域响应头默认不 expose ETag,改 MinIO CORS 配置又是部署负担。解法:**服务端回填**——completeUpload 时 ListParts 拿权威 etag,客户端报不报都行(schema 里 etags 保留,能报则省一次 ListParts 依赖)。
2. **DeleteBlob 撞外键**:谎报回收要删 blob 行,tasks 表还引用着它。迁移 `00002`:tasks / derivatives 的 blob 外键改 `ON DELETE CASCADE`。
3. **失败任务挡住重新校验**:EnqueueTask 最初 `ON CONFLICT DO NOTHING`,verify 失败后同 hash 再上传,任务表里躺着 failed 行,新任务进不去。改成失败任务重置回 pending。
4. **smoke 不幂等**:同一用户反复跑,used_bytes 越滚越大、秒传路径干扰断言。改成每次注册随机用户。
