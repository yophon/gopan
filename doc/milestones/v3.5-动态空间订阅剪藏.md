# v3.5 · 动态、空间、订阅与剪藏

> 按 doc/23 的计划交付四件事。**动态与撤回**:网盘里每一次改动都记下是谁(哪台设备、哪把应用密码、哪个 Agent、哪条收集链接、哪个后台任务)做的,移动 / 改名 / 删除 / 新建能单条、整组或按来源撤回,WebDAV 与 Agent 短时间大量删除时提醒。**空间分析**:类型、文件夹、大文件、重复文件、很久没动、空文件夹、闲置的分享与直链一页看清并清理;文件列表顺带改成自然顺序。**订阅**:RSS / 播客 / GitHub Releases 有新内容自动下进网盘。**剪藏**:网页正文存成 Markdown,Markdown 在网盘里直接渲染着看。不加系统包、不加环境变量、不加常驻组件;Go 库多了正文提取、HTML 转 Markdown 与 Markdown 渲染三个。服务端与网页一次上线(v3.5.0),安卓 App 3.5.0 同时带上。

## 关键决策

**动态记在服务层,不记在入口。** 网页、App、WebDAV、Agent 走的是同一批服务层方法,记在那里一处就全覆盖,也不会漏掉以后新加的入口;入口只负责把「是谁」放进 context。worker 里定稿的上传(浏览器分片上传、Agent 传输)拿不到请求的 context,所以开会话时把来源存进会话行。

**撤回只做可逆的动作。** 撤回 = 移动、改名、还原、进回收站,任何一步都不会真删东西,出错也能再撤回;覆盖与彻底删除没有可恢复的内容,明确标「不可撤回」,而不是假装能撤。批量撤回不是事务:每条各自成败、给原因,比「一条撤不了就全部回滚」更符合「尽量救回来」的用意。

**大量删除只提醒无人值守的来源。** 网页和 App 上的删除是自己点的,提醒只会烦人;WebDAV(rclone sync 方向搞反)、Agent、泄露的图床密钥才是需要「回头一看」的场景,提醒点进去就是撤回入口。

**Markdown 在服务端渲染。** 网页和安卓共用一套(网页 iframe、安卓 WebView),不在两个前端各加一个 Markdown 库;渲染结果与 `/x/` 的 SVG 一样放进沙箱,用户内容与网页同域也跑不了脚本。

**订阅解析自己写、流式读。** RSS / Atom 只需要标题、链接、附件、时间这几个字段,`encoding/xml` 加几百行就够;真实的播客订阅文件常有十几 MB,逐条解码读够 100 条就停,内存与文件大小无关。

**排序规则用 ICU 而不是在 Go 里排。** 文件列表是 keyset 分页,排序必须在数据库里、和翻页条件用同一个规则;ICU 的数字序与拼音序是现成的,确定性规则(相等即字节相等)保证游标不错位。没有 ICU 的 Postgres 回退字节序,迁移不失败。
