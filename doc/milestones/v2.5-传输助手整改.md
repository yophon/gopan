# v2.5 · 传输助手整改

> 对 v2.2 交付的传输助手做一轮可用性整改,计划见 doc/17。起因是两条用户反馈:"做得很不好用"和"页面停留久了发不出消息"。后者查下来不是断连,是前端把 `isIdle` 当成"没在发送中"用,第一条发出后按钮永久置灰。

## 关键决策

**文件进会话的职责从前端挪到服务端**。原来只有浏览器上传回调会补发 `sendChatMessage(nodeId)`,上传成功但补发失败就永远丢;WebDAV / Agent 放进同一文件夹的文件也不进会话。现在在 `CreateNode` 之后同事务插消息,三条上传路径一处钩子,任何渠道一致。不加唯一索引:存量数据可能已有重复文件消息,靠 `NOT EXISTS` 做幂等,避免迁移删用户数据。

**放宽 append-only,允许删单条**。误发、清理是传输助手的高频动作;只删消息不动文件,MCP 不暴露。不做批量清空、不做编辑。

**不做 SSE**。页面可见时 2s 轮询 + 回前台立即 refetch,单用户自用够用;真嫌慢再上 Postgres LISTEN/NOTIFY(doc/17 P1 第 5 项保留方案)。

**refresh 宽限期是兜底,前端互斥是主防线**。Web Locks + BroadcastChannel 让同一浏览器只有一个标签去刷新;旧 Safari 没有 Web Locks 时宽限期兜住。10 秒足够覆盖 Set-Cookie 落地的窗口,又远小于真实重放的时间尺度。

## 实现要点

- `InsertChatMessageForChatFolder` 一条 SQL 完成"指针校验 + 去重 + 插入":`INSERT … SELECT … FROM users WHERE chat_folder_id = $parent AND NOT EXISTS(…)`,没插返回 `ErrNoRows`,调用方当 no-op。
- WebDAV 覆盖 PUT 走 `ReplaceNodeBlob`,节点 id 不变,自然不重复落消息(dav/chat_test 验证)。
- 前端删除后把 id 放进 tombstone 集合:轮询请求可能在删除落地之前发出,返回的旧数据不再把它合并回来。
- 翻历史时记录 `scrollHeight` 与 `scrollTop`,插入后 `scrollTop = newHeight - oldHeight + oldTop`,视口钉在原来那条。
- 粘贴监听挂在 `document` 上(输入框没焦点时 Ctrl+V 也能发截图),`useEventListener` 随组件卸载。
- 搜索走 `['chatMessages','search',term]` 独立 queryKey,不污染轮询缓存;`invalidateQueries(['chatMessages'])` 前缀匹配会一并刷新。
