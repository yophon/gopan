# 13 · v2 规划

> 状态:**已执行完毕**(2026-07-12 规划,同日交付)。M7 → v1.1.0、M8 → v1.2.0、M9 → v1.3.0,合并发布 **v2.0.0**;每步实际落地见 doc/milestones/ 对应回顾。原规划的 M10(PWA/预览体验)仍未做;后续独立交付的 Remote MCP 归入 **v2.1.0**,不改写本篇历史计划,见 `doc/milestones/v2.1-MCP.md`。

## 一、v2 要解决什么

v1 交付的是"网页里好用的个人云盘"。真实使用一段时间后,剩下的痛点集中在三处:

1. **运营自己这台实例很原始**:注册关闭后建账号要上服务器敲 psql,调配额同理;任务队列健康、各用户用量,没有任何界面可看。→ 管理端
2. **规模上有已知的退化点**:目录分页是 offset(cursor 只是包装),大目录越翻越慢;文件夹不显示体积,想知道"哪个目录吃掉了配额"没有答案。→ 规模里程碑
3. **只有浏览器一个入口**:Finder/资源管理器挂载、rclone 同步、手机文件 App,全都进不来。→ WebDAV

三件事对应三个里程碑(M7~M9),外加一个机动的体验收尾(M10)。

## 二、原则

- **每个里程碑独立可上线、独立打 tag**:M7 → v1.1,M8 → v1.2,M9 → v1.3;三个都落地后打 **v2.0**。任何一个里程碑被砍,前面的交付不受影响。
- **不破坏 v1 合同**:GraphQL schema 只加不改(cursor 本来就是不透明字符串,keyset 替换不动接口);迁移全部带可回滚的 down;生产实例(2G 精简档)升级沿用 doc/09 镜像搬运流程,升级步骤写进上线手册。
- **质量闸门不降**:smoke + 浏览器探针全绿才提交;service 覆盖率不低于 73%;每个新面(管理端、WebDAV)配自己的 smoke。
- **资源红线**:精简档常驻内存不超 400MB(现约 350MB)。WebDAV 是常驻 handler 不是常驻进程,预算内。

## 三、范围总览

| 里程碑 | 主题 | 一句话 | 规模 | tag |

## 四、M7 · 管理端

**目标**:实例的日常运营(账号、配额、健康)全部界面化,不再登服务器。

**交付清单**

- 首个管理员的产生:CLI 子命令 `gopan admin promote <username>`(单二进制加子命令,零新依赖;比环境变量方案好在不用重启、不在配置里留敏感状态)。`is_admin` 列 M1 起就在,无迁移。
- Admin GraphQL:现有鉴权中间件已按 scope 分流,加一层 admin 校验(directive 或统一入口判断,开工时定);字段全部新增,不动既有 schema。
  - 用户:列表(用量/配额/状态)、创建、禁用/启用、重置密码(生成一次性新密码)、调配额。
  - 实例概览:总用量、用户数、任务队列(pending/running/failed 计数)、失败任务一键重试。
- 前端 AdminView:路由守卫(非 admin 404 而不是 403,不暴露路由存在)、用户表格、概览卡片。
- 禁用语义要定清楚:禁用 = 吊销全部 refresh family + 拒登录,**文件与分享保留**(冻结不是删除);被禁用户的活跃分享是否连带失效——倾向连带失效,开工时定案。

**不做**:审计日志(单管理员实例,审计自己没有意义,记入"将来如果多管理员再说");管理员代看用户文件内容(能看元数据用量,不开内容通道,边界写进 doc/12)。

**验收**:m7_admin smoke——promote → 建号 → 新号登录 → 调配额生效(initUpload 按新额拒绝)→ 禁用 → 该用户 refresh 失效且登录被拒。

## 五、M8 · 规模:keyset 分页 + 子树统计 + 基准

**目标**:把 v1 留的两处规模欠账清掉,并用数字证明——这是三个里程碑里唯一能产出性能数字的,复盘要带 benchmark 表。

**交付清单**

- **keyset 分页**:cursor 从"包装 offset"换成"排序键元组编码"。要处理的实际复杂度:三种排序(名/大小/时间)× 升降序 × folders-first 复合排序——keyset 条件是 `(is_folder, sort_key, id)` 三元组的行比较;搜索页(pg_trgm)一并换。合同不动:cursor 对前端始终是不透明字符串。`total` 字段保留(count 单独查,列表本身不再为翻页付 offset 代价)。
- **子树体积/数量**:两个方案开工时二选一,先写下取舍——
  - A. 物化:nodes 加 `subtree_bytes/subtree_count`,写路径(上传/删除/移动/复制)在事务内沿祖先链更新。读零成本,写路径加宽,移动大目录时祖先链更新最重。
  - B. 异步:变更把受影响的目录标脏,worker 批量重算,前端显示"约 X GB(统计中…)"。写路径零负担,数据最终一致。
  - 倾向 B——与既有 tasks/worker 模型同构,且云盘对"文件夹大小"本来就不要求强一致。
- **前端**:列表文件夹显示体积;搜索/列表滚动加载贴 keyset。
- **基准**:造数脚本(10 万节点单目录、100 万节点全库)入 scripts/;对比 offset vs keyset 的 P50/P99(翻到第 1 页 / 第 100 页 / 最后一页),子树统计的重算耗时。数字进复盘。

**验收**:既有 smoke 全绿(分页替换对外无感的直接证明)+ 基准数字达标(深翻页不随页深退化)。

## 六、M9 · WebDAV(最大块,拆两段)

**目标**:标准协议入口。挂载到 Finder/资源管理器、rclone 备份、手机文件 App 三个场景跑通。

**先定死的三个设计决策**

1. **认证用应用密码,不用主密码**:WebDAV 客户端只会 Basic Auth,主密码走 Basic 意味着明文密码存在每台设备的钥匙串里,且 bcrypt(cost 12)每请求验一次是自己 DoS 自己。做 `app_passwords` 表:随机生成、只显示一次、存 sha256(与 refresh token 同构)、每设备一条、可单独吊销、scope 限 webdav。
2. **WebDAV 写入的字节流过 Go,接受它**:协议就是 PUT 整个 body,没有预签名的余地。这是"字节流不过 Go"原则的**显式例外**:兼容层按兼容层计费——流式收 body、边收边算 SHA-256、multipart 转存 MinIO,完成后与既有 blob 模型合流(hash 命中则丢弃临时对象、ref+1,变相秒传);挂 /pack 同款限速闸。
3. **库的选型**:适配 `golang.org/x/net/webdav` 的 FileSystem 接口(node/blob 模型实现它的 os 风格接口),LOCK 用它自带的内存锁(单机够用)。手写 handler 只在适配成本被证明更高时才考虑——开工首日先做适配 spike,一天内见分晓。

**分段交付**

- **9a 只读**(先上线):OPTIONS/PROPFIND/GET/HEAD + 应用密码 + 前端"应用密码管理"页。验收场景:rclone ls/copy、Finder 只读挂载、手机 Documents 浏览下载。
- **9b 读写**:PUT/MKCOL/DELETE/MOVE/COPY/LOCK。语义全部复用 service 层:DELETE=软删进回收站、同名自动改名规则一致、配额检查一致、MOVE 防成环一致。验收场景:Finder 读写挂载(LOCK 的真实考验)、rclone sync 双向。

**风险(v2 最大)**:客户端兼容性是泥潭——Finder、Windows 资源管理器、rclone 对 PROPFIND 深度、ETag、锁的实现各有脾气。对策:验收就按"三客户端场景清单"来,不追协议完备,追实测可用;9a/9b 分开上线,9b 不顺可以只交 9a 也是完整交付。

**验收**:m9_webdav smoke(litmus 协议测试套挑核心子集 + 三客户端手测清单);WebDAV 上传的文件走 verify_hash 全链(谎报回收对 WebDAV 入口同样生效)。

## 八、顺序为什么是这样

- **M7 先行**:最小、自用最痛(建号)、且管理端的"任务队列可视"给 M8/M9 的 worker 类工作提供观察窗。
- **M8 居中**:清合同欠账(keyset 是 v1 复盘里点名的后路),产出性能数字;子树统计的异步方案跑在 M9 之前,让 worker 模型先多一个消费者练手。
- **M9 最后**:最大、风险最高、且 9a/9b 天然分段——就算 v2 周期被打断,砍在任何一刀,前面都是完整交付。
- 版本节奏配合:每个里程碑一个 minor tag,生产实例随升(顺带验证升级手册),v2.0 是水到渠成的一刀而不是大爆炸发布。
