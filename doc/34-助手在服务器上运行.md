# 34 · 助手在服务器上运行

> doc/33 的助手跑在客户端里：网页关掉、手机锁屏，这一轮就停了。这里加第三种运行方式：交给服务器跑，客户端关掉也照样跑完；任何设备打开这个对话都能看到进度、确认、停止。转发 / 直连两种照旧。

## 一、用的人看到的

- **怎么开**：面板（网页）/ 助手页（App）输入框里的云朵按钮「在服务器上运行」，亮着是开，按对话记。开着时发出去的话交给服务器跑，关着就和现在一样在本机跑。
- **看进度**：任何设备打开这个对话，都能看到它跑到哪了（正在打的字、调了哪些工具），和本机跑时一样。对话记录列表里，正在跑的标「运行中」，等确认的标「等你确认」。
- **确认**：遇到要「询问」的操作（改、删、分享、存入……），这一轮停在确认卡上，并推一条通知「助手等你确认：移动 12 项到『报销』」（站内通知、App 通知、ntfy / Bark / Telegram，按通知设置走）。任何设备点「允许 / 这次对话都允许 / 不行」，它就接着跑。一直没人管，24 小时后这一轮自动结束。
- **停止**：任何设备都能点「停止」。
- **做完了**：跑了超过 1 分钟才结束的，发一条通知「助手做完了：……」。
- **规则不变**：权限三态、目录范围、停用助手、动态来源「助手」、整批撤回，和本机跑时完全一样；拒绝的照样拒绝，询问的照样要人点。
- **模型**：站点提供的、自己的都行，都经服务器转发；站点额度照样计。

## 二、整体结构

```
客户端(网页 / App)           gopan(Go)                                   qjs 进程(每一轮一个)
  发消息 ── startAiRun ──▶  ai_runs 记一行(queued)
                             排到了:起一个 qjs,喂 runtime ──────────────▶ runtime.ts 跑这一轮
                             ◀── 标准输出:要发请求 / 要等 / 事件 / 要确认 ──
                             替它发请求(本机的 /query /mcp /api/ai 带运行凭证)
                             ── 标准输入:响应头、一块块响应体、醒、答复、停 ─▶
  SSE 收到「助手」事件 ◀──── 推给这个用户的所有设备
  点允许 ── answerAiRun ──▶  ── 标准输入:答复 ──────────────────────────────▶ 接着跑
```

- **引擎**：QuickJS 的社区维护版 quickjs-ng 自带的命令行程序 `qjs`（静态编译，约 2.5 MB），放进服务器镜像。每一轮起一个进程，跑完就退出；轮与轮之间互相隔离，每个进程限内存，停止时直接结束进程，一轮出问题拖不垮 gopan。
- **代码**：跑的就是网页、App 用的那份 `web/src/assistant/runtime.ts`，换一个入口 `qjs-entry.ts`：宿主函数不再是 Kotlin / 浏览器提供，而是一行行 JSON 经标准输入输出和 Go 来回传。打包进 gopan 的二进制（`go:embed`），起进程时写到临时文件。
- **qjs 里什么都不用自己等**：网络、等待（超时计时、重试退避）都交给 Go，到点或数据来了 Go 往标准输入写一行，JS 这边只管读。Windows 版 qjs 在等标准输入时计时器会被耽误，这样也一并躲开了。随机数用 `Math.random`（只用来生成条目 id，不涉及安全）。
- **对话记录**本来就按条存在服务器上（doc/33 三），服务器跑的一轮同样一条条追加，客户端打开对话读到的就是最新的。正在打的字、确认卡这些「过程中」的东西不落库，经现有的推送通道（doc/32 的 `/api/events`）推给这个用户的设备。

## 三、服务端

### 运行记录

- 新表 `ai_runs`：`id`、`user_id`、`conversation_id`、`status`（`queued` / `running` / `waiting`（等确认）/ `done` / `failed` / `stopped`）、`input`（这句话、「你在看什么」、服务与模型）、`approval`（等确认时的确认卡 jsonb）、`error`、`created_at`、`started_at`、`finished_at`。
- 一个对话同时只能有一轮在跑。`ai_conversations` 加 `runner`（`device` / `server`）记开关。
- GraphQL：
  - `startAiRun(conversationId, text, context, providerId, model)`：没有对话就先建；排队。
  - `aiRun(conversationId)`：这个对话当前这一轮的状态与确认卡（打开对话时用）。
  - `answerAiRun(id, answer)`：`once` / `session` / `deny`。
  - `stopAiRun(id)`。
  - `setAiConversationRunner(id, runner)`：开关。
  - `aiConversations` 每行带上 `runner` 与当前这一轮的状态（列表上的「运行中」「等你确认」）。
- 推送：`/api/events` 多一种 `{"t":"assistant","c":"<对话 id>","e":{…}}`，`e` 是运行时交出来的事件（items / live / conversation / error），外加 `{"type":"run","run":{…}}`（状态、确认卡）。

### 一轮怎么跑

- 进程内的调度：同时最多 `GOPAN_AI_RUNS` 轮（默认 2），每人同时 1 轮，多的排队（按创建先后）。服务重启时，没跑完的标 `failed`「服务重启,这一轮中断了」。
- 起进程：`qjs --std --memory-limit 131072 --stack-size 1024 <runtime.js>`（128 MB、1 MB 栈）；找不到 `qjs`（`GOPAN_QJS`，默认 `/usr/local/bin/qjs`）时这个功能报「服务器上没装助手运行环境」。
- **请求**：JS 要发的请求由 Go 发。发给 gopan 自己的（`/query`、`/mcp`、`/api/ai`）走本机回环地址，Host 与 `X-Forwarded-*` 填站点的对外地址（工具返回的分享链接才是对外的），带一张运行凭证；发给别处的照常发（服务器上用不到，模型都经转发）。
- **运行凭证**：Go 每次发请求时现签一张短时 JWT，scope `ai-run:<对话 id>`，用户是对话的主人。它能用的只有：
  - `/mcp`：按助手的身份与权限，和客户端带 `X-Gopan-Assistant` 时一样；对话 id 必须对得上。
  - `/api/ai`：转发，额度照算。
  - GraphQL 的 `assistantAccess`、`aiConversation`、`aiEntries`、`appendAiEntries`、`node`（确认卡上按 id 查名字）；对话只能是这一个。
  - 别的一律 FORBIDDEN。助手停用、用户被禁用时 `/mcp` 照样拒绝。
- **确认**：JS 要确认时，Go 把这一轮标 `waiting`、存下确认卡、推送、发通知，等任何设备 `answerAiRun`；等确认的时间不算进一轮 30 分钟的上限。
- **停止**：`stopAiRun` → Go 往标准输入写「停」，运行时自己收尾（把已有的写进对话记录）；5 秒还没退出就结束进程。
- 一轮最长 30 分钟（不算等确认），最多 100 次工具调用；等确认最长 24 小时。超了按停止处理。

### 部署

- `Dockerfile.prebuilt` 下载 quickjs-ng 的 `qjs-linux-x86_64`（固定版本与 sha256 校验）放到 `/usr/local/bin/qjs`。
- 不加容器、不加密钥。

## 四、客户端

- **网页**：输入框里的云朵按钮；对话是服务器跑的时候，面板不建 Agent，发消息走 `startAiRun`，画面由推送事件驱动（和本机跑用的是同一套显示），确认卡答复走 `answerAiRun`，停止走 `stopAiRun`。现有本机运行的代码不变。
- **App**：同样。服务器跑的对话不用 QuickJS，`ChangeStream` 多认一种 `assistant` 事件；App 在后台时收不到推送，确认靠通知点进来。
- 一个对话能切换：切到服务器，下一句开始由服务器跑；切回本机同理。正在跑的那一轮不能切。

## 五、不做的

- 定时任务：服务器能自己跑之后顺手就能做，这次不做，记在 doc/28 备选。
- 本机正在跑的一轮中途交给服务器：本机那份 Agent 的状态在内存里，不迁移；下一句再切。
