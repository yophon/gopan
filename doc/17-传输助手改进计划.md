# 17 · 传输助手改进计划

> 对 v2.2 交付的「传输助手」(`/chat`,ChatView + service.Chats)做一轮可用性整改。实施结果与取舍见 `doc/milestones/v2.5-传输助手整改.md`。本文先列代码里能确认的问题,再按三期给出改动项、涉及文件与验收标准。架构决策(单会话、append-only、附件落「我的设备」文件夹)保持不变,只在明确说明处放宽。

## 一、现状问题(按使用链路)

### 0. 每次进入页面只能发一条文本(表现为"停留久了就发不出去")

`ChatView.vue` 的 `send()` 与发送按钮都用 `sendMutation.isIdle` 当"没有在发送中"的判断。TanStack Query v5 的 mutation 状态机是 `idle → pending → success | error`,`isIdle` 只在**第一次** `mutate` 之前为 true,成功后停在 `success`,不会自动回到 `idle`(除非显式 `reset()`)。结果:

- 第一条文本发出后按钮永久置灰,Enter 走到 `send()` 直接 `return`,没有任何提示。
- 文件发送不经过这个 mutation,仍然能传,更显得"文本莫名发不了"。
- 离开 `/chat` 再回来会重建 observer,又能发一条。用户体验上就是"开页面能发,待一会儿就不行"。
- 伴生问题:轮询请求会在 access token 过期时走 401 → 单飞 refresh → 重放,本身是正常的;但同一浏览器开两个标签页时,两边各自持有内存里的 access token,若在同一秒内同时 401 并用同一个 refresh cookie 去刷新,后到的一方命中 `UsedAt` 重用检测,整个 family 被吊销,两个标签都被踢回登录页。这是真正意义上的"断连",与上面的 bug 独立,但发生概率低得多。

修法:`isIdle` 改为 `!isPending`(仓库里其他 8 处 mutation 用的都是 `isPending`,只有这里写错)。多标签 refresh 竞争在 P1 第 6 项处理。

### 1. 发文本

| 问题 | 代码依据 |
|---|---|
| 单行输入框,Enter 即发,无法换行;手机上 Enter 也会直接发出 | `ChatView.vue` composer 用 `el-input` 默认 type,`@keyup.enter="send"` |
| 发送后不上屏,要等 mutation 回来再 `invalidateQueries` 再 refetch,两次往返才看到自己的消息 | `sendMutation.onSuccess` 只做 invalidate,没有乐观插入 |
| 多行文本显示成一行 | `.bubble` 没有 `white-space: pre-wrap`;Agent 经 `chat_send` 发的多行文本会被压扁 |
| 文本不能一键复制、URL 不可点、长文本不折叠 | bubble 是纯 `{{ message.body }}` |

### 2. 传文件

| 问题 | 代码依据 |
|---|---|
| 点回形针 → toast「已加入 N 个上传任务」→ 聊天区没有任何进度,传完才突然出现卡片;进度在另一个 UploadDrawer 里 | `sendFiles` 只 `enqueueFiles` + `ElMessage.success` |
| 上传成功但 `sendChatMessage` 失败时,文件已在网盘里、会话里永远没有这条,只有一个 toast,无重试 | `setUploadDoneListener` 回调 `.catch(() => ElMessage.error(...))` |
| 刷新页面 / 切走再回来,未完成的上传丢失(iOS 回收标签页时尤甚);`chatFolderId` 是模块级变量,重载后要等 `chatFolder` 查询回来才能正确判定 | 见 doc/14 已知问题;`let chatFolderId` 模块级 |
| 不支持粘贴截图(Ctrl+V)、不支持拖文件到聊天区 | 没有 `paste` / `drop` 处理 |
| 图片缩略图 44px,截图看不清内容,必须点开 | `.file-thumb { width: 44px; height: 44px }` |
| 一次选多个文件 = 多条消息,刷屏 | 每个 `UploadTask` 完成各自发一条 |
| WebDAV / MCP 直接往「我的设备」文件夹放的文件不会进会话 | 消息只在前端 upload 回调里写,服务端不感知 |

### 3. 看历史

| 问题 | 代码依据 |
|---|---|
| 打开页面停在顶部,新消息到了也不滚动,看不见 | 没有任何 scroll 逻辑 |
| 只有最近 200 条,没有「加载更早」;后端 `before_id` 游标已经做了,前端没接 | `useQuery` 固定 `limit: 200`;`ListRecent` 支持 `last` |
| 只显示 `HH:MM`,没有日期分隔,跨天消息分不清 | `timeOf` 只取时分 |
| 无搜索、无删除 | append-only 决策;但误发/清理是传输助手的高频动作 |
| 跨设备最长等 5s 才看到;「已连接」标签是常量,不反映真实状态 | `refetchInterval: 5000`;`<el-tag>已连接</el-tag>` 写死 |

### 4. 命名

侧栏叫「传输助手」,文件夹和所有错误文案叫「我的设备」,页面标题下又写「在电脑和手机之间传输消息与文件」。三个名字指同一件事。

## 二、改进计划

### P0 · 纯前端整改(不动 schema,约 2–3 天)

目标:把「发得出、看得见、传得稳」三件事做顺。

0. **修 `isIdle` bug(先于一切,单独一个提交)**
   - `send()` 与按钮 `:disabled` 改用 `sendMutation.isPending.value`。
   - 补 Vitest:连续 `send` 两次都进入 mutation。
1. **自动滚底 + 新消息浮标**
   - 首次加载、发送成功、轮询到新消息且用户在底部附近(< 80px)时 `scrollTo` 底部。
   - 用户在上方翻历史时不打断,改为底部浮出「N 条新消息 ↓」按钮。
   - 文件:`ChatView.vue`。
2. **乐观上屏 + 失败重试**
   - `send()` 立即插入本地 `pending` 消息(临时 id、灰色气泡、「发送中」),mutation 成功后用服务端消息替换,失败则标红并给「重试」。
   - `mergeChatMessages` 增加 pending 列表参数,去重时以服务端为准。
   - 文件:`ChatView.vue`、`utils/chat.ts`(+ Vitest)。
3. **多行输入**
   - `el-input type="textarea" :autosize="{minRows:1,maxRows:6}"`。
   - 桌面:Enter 发送、Shift+Enter 换行;手机:Enter 换行、只靠按钮发送(用 `isMobile`)。
   - `.bubble` 加 `white-space: pre-wrap`。
4. **气泡可操作**
   - URL 自动转链接(`linkify` 轻量实现,`rel="noopener"`)。
   - 悬停/长按出「复制」;超过 8 行折叠,点「展开」。
5. **粘贴与拖拽**
   - 聊天区 `@paste`:`clipboardData.files` 非空 → 走 `sendFiles`;截图默认命名 `截图 2026-10-13 14-30.png`。
   - 聊天区 `@dragover/@drop`,拖入时整块高亮「松开发送」。
6. **聊天内上传进度卡片**
   - `sendFiles` 入队时就在消息流里插入占位卡片(文件名、大小、进度条、取消),数据直接读 `useUploadsStore` 里对应 `task.id` 的 progress。
   - 完成 → 占位卡片被真实消息替换;失败 → 卡片标红,可「重试」(重新 enqueue)或「移除」。
   - 文件:`ChatView.vue` + 新 `components/chat/UploadingCard.vue`。
7. **文件消息发送失败兜底**
   - 上传完成而 `sendChatMessage` 失败的 `nodeId` 写入 `localStorage`(`chat:pendingNodes`),页面加载和每次轮询后重试;重试成功后清除。
   - 这是 P1 第 1 项落地前的临时方案,P1 落地后删掉。
8. **列表展示**
   - 日期分隔线(今天 / 昨天 / 具体日期),时间保留 `HH:MM`。
   - 图片/视频卡片改为大图(最宽 240px,保持比例),其他文件维持小卡片。
   - 「已连接」改为真实状态:轮询连续失败 ≥ 2 次显示「离线,重连中」,恢复后回到「已连接」;或直接去掉这个标签。
9. **命名统一**
   - 前端所有「我的设备」文案改为「传输助手」;`chatFolderName` 常量暂不动(数据库里是用户数据,见 doc/14)。

验收:
- 手机 + 电脑各开一个标签页,一端发文本,本端立即上屏,另一端 5s 内滚到底看见。
- Ctrl+V 一张截图,聊天里立刻出现进度卡,完成后变成大图卡,点开能预览。
- 传一个 100MB 文件中途断网再恢复,卡片进入失败态并能重试;刷新页面后 pendingNodes 不丢消息。
- vue-tsc、Vitest、vite build 全过。

### P1 · 后端小改(约 2–3 天)

目标:把「文件进会话」的职责从前端移到服务端,接上历史与删除。

1. **服务端自动落消息**
   - `completeUpload` 成功且 `parent_id == users.chat_folder_id` 时,在同一事务里 `InsertChatMessage(node_id)`。
   - 同样钩子加到 WebDAV `PUT` 完成与 MCP `complete_upload`:任何渠道放进该文件夹的文件都进会话。
   - 前端删掉 `setUploadDoneListener` 里的发消息逻辑与 P0 第 7 项的 localStorage 兜底。
   - 幂等:`chat_messages` 上加 `(owner_id, node_id)` 部分唯一索引(`WHERE node_id IS NOT NULL`),重复完成不重复发。
   - 文件:`service/upload.go`、`service/chat.go`、`webdav/`、`mcpserver/server.go`、迁移 `00016`。
2. **加载更早**
   - schema:`chatMessages(limit: Int = 200, before: ID)`,resolver 透传到 `ListRecent(last)`。
   - 前端:滚到顶部触发 `fetchPreviousPage`(改用 `useInfiniteQuery`),保持滚动位置不跳。
3. **删除消息**
   - 放宽 append-only:新增 `deleteChatMessage(id: ID!)`,只删消息行,不动文件(文件仍在「我的设备」文件夹,要删走网盘回收站流程)。
   - 这是面向「误发/清理」的最小放宽;不做批量清空、不做编辑。
   - MCP 不暴露删除(与现有「不暴露永久删除」原则一致)。
4. **搜索**
   - `chatMessages(query: String)`:`body ILIKE` 或关联 node `name ILIKE`,仍受 limit 约束。
   - 前端 header 加搜索框,结果列表点一条跳到上下文(用 `before` 游标从该条往前取)。
5. **实时性**
   - 先做低成本版:页面可见时 `refetchInterval` 降到 2s,`visibilitychange` 回到前台立刻 refetch。
   - 如果仍嫌慢再上 SSE:`GET /api/chat/events`,服务端用 Postgres `LISTEN/NOTIFY chat_<owner>`,`InsertChatMessage` 后 `NOTIFY`;前端 `EventSource` 收到即 invalidate。单用户单会话,不需要 WebSocket。
6. **多标签页 refresh 竞争**
   - 前端:`singleFlightRefresh` 跨标签互斥,用 `navigator.locks.request("auth-refresh")` 包住,拿到锁后先检查 `accessToken` 是否已被别的标签换新(通过 `BroadcastChannel("auth")` 广播新 token),是则直接复用不再请求。
   - 后端:`Refresh` 对 `used_at` 在 10 秒内的 token 做宽限,返回同 family 最新一枚而不是吊销(常见的 rotation grace 做法),把误杀留给真正的重放。
   - 验收:同一浏览器开两个 `/chat` 标签页放 20 分钟,两边都不掉登录。

验收:
- 用 rclone 往「我的设备」丢一个文件,5s 内会话里出现卡片。
- `chat_integration_test.go` 加 `before` 游标分页、删除后 `chat_list` 不再返回、重复 `complete_upload` 只产生一条消息。
- 浏览器从 1000 条历史往上翻,无跳动,每页 100 条。

### P2 · 体验增强(视需要,各项独立)

1. **多文件合一条**:schema `sendChatMessage(nodeIds: [ID!])` + `ChatMessage.nodes`,一次选 5 张图显示为九宫格。需要新迁移(`chat_message_nodes` 关联表),改动面较大,放最后。
2. **剪贴板直通**:header 加「复制最新文本」按钮;手机端收到文本消息气泡上默认露出复制图标。
3. **Web Share Target**:PWA `manifest.share_target` 指向 `/chat?share`,Android 任意 App 的「分享」菜单可直接发到传输助手(iOS 不支持,忽略)。
4. **消息来源标记**:`chat_messages.source` 列(`web` / `mcp` / `webdav`),气泡角上小图标。对 Agent 用户有意义,普通用户可隐藏。
5. **文本转文件**:超过 4000 字的粘贴自动存为 `.txt` 文件消息,而不是报「消息最长 4000 字」。

## 三、实施顺序与分支

- P0 一个分支 `feat/chat-ux`,一次 PR,顺序按上面 1→9,每项独立提交。
- P1 第 1 项(服务端落消息)优先级最高,单独分支 `feat/chat-server-side-message`,先于其余 P1 项合入,合入后删 P0 第 7 项。
- 其余 P1 / P2 各自独立 PR。
- 每期合入后更新 doc/05、doc/07、doc/11、docs/MCP.md 对应段落,milestones 下补 `v2.5-传输助手整改.md`。
