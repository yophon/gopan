# 36 · 局域网直传计划

> 传输助手经过服务器:手机传给电脑,文件先传到 VPS 再下回来,大文件慢,还走两遍流量。这里给桌面端和安卓端加「直传」:同一个局域网里的设备直接互传,字节不经过服务器。自己账号的设备、别人的设备都能传,也能和装了 [LocalSend](https://github.com/localsend/localsend) 的设备互传——直接用 LocalSend v2 协议,不另造一套。收到的文件默认存在本机,想放进网盘再点一下。网页端不做。

## 一、用的人看到的

- **附近设备**:桌面端托盘菜单「直传」打开一个小窗,安卓 App 里有「直传」页。列出同一个网络里的设备:自己账号的(标「我的设备」)、别人的 gopan、LocalSend。
- **发**:选设备 → 选文件 / 文件夹 / 一段文字 → 发。桌面端还可以拖进小窗、资源管理器右键「直传到…」;安卓可以从系统分享菜单选「gopan 直传」。
- **收**:自己账号的设备发来的,直接收下(设置里可以关);别人的弹窗问「接收 / 拒绝」,可以勾「以后自动接收这台设备」。文字消息只显示,不存文件,可以复制。
- **存在哪**:桌面端存到设置里的直传目录(默认「下载\gopan 直传」),安卓存到「Download/gopan」。网盘里没有这些文件。
- **进网盘**:直传记录里每一条都有「存到网盘」,选一个文件夹(默认「我的设备」),交给现有的上传队列。
- **没联网也能用**:直传不依赖服务器。没登录、服务器连不上的时候,和 LocalSend、别人设备的互传照常;自己的设备按上次从服务器拿到的指纹照样认得(见三),只是新登录的设备要等连上服务器才认得。
- **看不到对方时**:路由器开了 AP 隔离、公司网络屏蔽组播等情况下,自己账号的设备仍能靠服务器找到对方(见三)。别人的设备只能靠组播和扫描网段,找不到就是找不到,界面上写清楚可能的原因。

## 二、整体结构

```
     桌面端(Tauri)                         安卓 App
  ┌──────────────────┐                ┌──────────────────┐
  │ nearby 小窗(本地页)│                │ 直传页(Compose)    │
  │   ↕ IPC           │                │   ↕ JNI(uniffi)   │
  │ lanshare(Rust)    │ ◄── HTTPS ───► │ lanshare(Rust)    │
  │  └ localsend core │   组播 UDP     │  └ localsend core │
  └────────┬─────────┘                └────────┬─────────┘
           │ GraphQL:登记自己 / 查自己的其他设备   │
           │ SSE:{"t":"lan"}                      │
           └──────────────► gopan 服务器 ◄───────┘
                     (只交换地址和指纹,不碰文件)

  LocalSend 官方客户端 ◄── 同一套 v2 协议 ──► 上面两者
```

- **协议**:LocalSend Protocol v2(组播发现 `224.0.0.167:53317`、`/api/localsend/v2/register`、`prepare-upload`、`upload`、`cancel`;HTTPS 用自签证书,指纹是证书的 SHA-256)。v3(nonce 换签名令牌、配对)还没定稿,先不跟。
- **实现**:新建 Rust crate `lanshare`,包一层 LocalSend 的 `packages/core`(Apache-2.0,crate 名 `localsend` 0.1.0,特性开 `discovery` + `http`,不开 `webrtc`)。core 已经把 v2 服务端做成库,通过 `mpsc` 发 `ServerEventV2` 给应用:
  - `Register`:有设备登记;TLS 下只有登记里报的指纹和握手时的证书一致才发。
  - `PrepareUpload`:带 `decision_tx`(全收 / 收一部分 / 拒绝)和 `cert_fingerprint`(握手时校验过的客户端证书指纹,伪造不了)。
  - `FileUpload`:带 `target_tx`,由应用决定写到哪(流、路径或文件描述符)。
  - `SessionEnd`、`PrepareUploadAborted`、`CancelReceived`(对方取消我们正在发的)、`ListenerFailed`(监听挂了,要应用重启服务)。
- **LocalSend 官方客户端自己也用这套 core**:1.18(2026-08)起它的网络层已经换成 Rust core(1.18.2 修的「TLS info not found」是 Rust 网络库那边的报错),所以我们和官方 1.18 以后的版本跑的是同一份协议实现。
- **为什么两端都用 Rust**:协议、证书、指纹校验只写一份。桌面端外壳本来就是 Rust,而且依赖已经对得上(reqwest 0.13 + rustls/ring)。安卓端经 uniffi 生成 Kotlin 绑定,LocalSend 自己的安卓版也是这样(flutter_rust_bridge)接的 core。安卓能不能这么做要先实测(见六的 L0),不行就退回 Kotlin 自己实现。
- **core 没发到 crates.io**,main 每天都在推,v3 也在开发中,0.1.0 的接口随时会变。所以不用 git 依赖,而是把钉住的那个 commit 拷进仓库(和 `web/src/vendor/tau` 一样),附 `SOURCE.md` 写明来源、commit、许可证;升级时对一遍 v2 接口再换。
- **依赖对得上**:core 用的 reqwest 0.13(`rustls-no-provider`)、rustls 0.23(ring)和桌面端现在用的一致;sha2 core 用 0.11、桌面端用 0.10,会同时编进两份,能编,只是多一点体积。

## 三、服务器帮忙认出自己的设备

只交换「我在哪、我是谁」,不经手文件。

### 登记

- 新表 `lan_devices`:`family_id`(主键,外键到 `sessions`,删除时级联)、`user_id`、`fingerprint`、`alias`、`device_type`、`addrs`(局域网地址列表)、`port`、`public_ip`(服务端从请求里取,和 `sessions.ip` 用同一套取真实 IP 的逻辑)、`updated_at`。
- 一台设备就是一个登录会话(`sessions.family_id`),所以「登录设备」里移除这台设备,它的直传登记也跟着没了;改密码、被管理员禁用,整族吊销,同样作废。
- GraphQL:`announceLan(input)` 在启动、网络变化时调用,之后每 10 分钟调一次;`lanPeers` 返回同一用户、30 分钟内登记过、会话没有吊销的其他设备。`addrs` 只收私有地址(IPv4 的 10/8、172.16/12、192.168/16,IPv6 的 ULA 和全局地址),回环、链路本地一律丢掉。
- 推送:登记变化时在事务里 `pg_notify` 发 `{"t":"lan"}`,接收端重新拉 `lanPeers`(走 doc/32 现成的 `ChangeHub`)。
- 登出:客户端先注销登记,然后本地清掉「自己账号的设备」列表。

### 找到对方

- 用 core 现成的 `discover_staged(known_channels, interface_ips, …)`:先发组播公告、同时并发探测已知地址;过一小段时间还没有任何回应,再扫本机所在的 /24 网段。已知地址就填 `lanPeers` 给的地址(公网出口 IP 相同的排前面,不同的也试,双栈、IPv6 下出口 IP 未必一样)。
- 探测就是向对方 `POST /api/localsend/v2/register`。TLS 握手时拿到对方证书,**算出来的指纹必须和服务器给的一致**,才算「我的设备」。
- 这一条兜的是组播不通的情况。组播能通的时候,两边本来就能互相看到,服务器只负责给出「这台是你的」这个标记。
- **本机缓存**:每次拉到 `lanPeers` 就把这些设备的指纹存在本机;服务器连不上时按缓存认自己的设备。登出时清掉。

### 免确认靠什么

- core 的客户端每次请求都出示自己的证书;服务端在不开网页分享(我们不开)时**强制**要求对方出示客户端证书。所以经 HTTPS 发来的 `prepare-upload` 一定带着 `cert_fingerprint`,指纹冒充不了。
- 规则:`cert_fingerprint` 在「我的设备」列表(或本机缓存)里 → 直接收下;不在 → 按陌生设备弹窗。
- 官方 LocalSend 1.18 以后跑的就是 core,同样出示证书,能连上我们,发来的照常弹窗。1.17 及更早的老版本(Dart 网络层)在强制客户端证书下可能连不上我们,L0 拿一台实测;连不上就在使用手册里写「请升级到 1.18 以上」,不为它放宽成可选证书。

## 四、两端怎么做

### 共用的 `lanshare`(Rust)

- 证书:第一次启动时用 core 的 `generate_self_signed()` 生成自签证书和私钥(RSA-2048,为了兼容老的 Flutter 版;生成要一会儿,放后台线程,不卡启动),存到本机配置目录;指纹就是证书的 SHA-256。重装或清数据会换指纹,在服务器那边就成了一台新设备,旧的登记 30 分钟后过期。
- 服务端:监听 53317(被占了就往后找,对方从公告里拿到实际端口),只开 v2 路由,不开 web 分享页;`verify_checksums` 打开;每次只收一个会话,忙的时候返回 409(协议规定)。
- 和本机装着的 LocalSend 共存:core 的组播 socket 设了地址 / 端口复用,两边都收得到组播;只有 HTTP 端口会撞,按上一条往后找。
- 发现:组播公告;收到公告后回 `register`。组播不通时,对本机所在的 /24 网段做一次 HTTP 扫描(协议 3.2),只在用户手动点「刷新」时才扫。
- 发送:`prepare-upload` → 并发 `upload`(每批 3 个)→ 失败或取消时调用 `cancel`。文字消息按 LocalSend 的做法:作为 `text/plain`、`preview` 里放正文,对方返回 204 就算发完。
- 记录:本机 SQLite 一张 `lan_history` 表(方向、对方别名和指纹、文件名、大小、本地路径、时间、是否已存网盘),「存到网盘」读的就是它。
- 对外接口(给 Tauri 命令和 uniffi 用):`start(config)`、`stop()`、`peers()`、`send(peer, items)`、`cancel(id)`、`answer(session_id, accept, remember)`、`set_known_devices(list)`,再加一个事件流(发现设备、来了请求、进度、完成、失败)。

### 桌面端

- `desktop/src-tauri/src/lan.rs`:起停 `lanshare`、桥接事件、通知(「收到 3 个文件」点一下打开所在文件夹);每次网页交来 token 时,顺带调用 `announceLan` 并拉取 `lanPeers`。
- **直传小窗用本地页面** `desktop/src/nearby.html`,和设置页一样打包在程序里。不用远程网页的原因:服务器连不上时直传必须照样能用,而远程网页那时根本打不开。
- 资源管理器右键、「发送到」加一项「直传到…」,参数照 `shell.rs` 现有做法攒成一批,打开小窗让用户选设备。
- 「存到网盘」:小窗里点了之后,交给主窗口的网页弹出文件夹选择框(复用 `DesktopUploadPicker`),选完进现有的 `transfer/upload.rs` 队列。
- **Windows 防火墙**:安装包是按用户装的、不要管理员权限,装的时候加不了放行规则。第一次监听端口时系统会弹窗,用户点了取消就收不到文件,但发送不受影响。小窗检测到「组播收不到任何东西 / 别人连不进来」时,提示去防火墙放行。网络类型是「公用网络」时,默认规则也会挡住入站,同样要提示。具体怎么检测,L1 实测后再定。

### 安卓

- `lanshare` 交叉编译成 `arm64-v8a` 和 `x86_64`(App 现在只发这两种)的 `.so`,uniffi 生成 Kotlin 绑定,放在 `core/lan/`;界面放在 `feature/lan/`。x86_64 只给模拟器用,模拟器里组播基本收不到,直传要在真机上测。
- 体积:`.so` 里有 reqwest、hyper、rustls、ring、rsa、x509-parser,估计每种 ABI 多几 MB(APK 现在 7.6 MB),L0 实测记下。
- 组播:要申请 `WifiManager.MulticastLock`,加 `CHANGE_WIFI_MULTICAST_STATE` 权限(普通权限,不用弹窗)。
- 局域网权限:Android 17 起访问局域网要 `ACCESS_LOCAL_NETWORK`(LocalSend 1.18.1 就是为这个补的)。L3 对照官方文档确认是否要运行时申请、用户拒绝时怎么提示。
- 接收:App 在前台时一直开着;在后台时由用户在直传页打开「保持可接收」,起前台服务,类型用 `connectedDevice`(「需要网络连接的外部设备交互」),不用 `dataSync`:
  - `dataSync` 从 Android 15 起(target 15 以上)24 小时内总共只能跑 6 小时,到点系统调 `onTimeout()`,几秒内不停就抛异常;同一应用所有 `dataSync` 服务共用这 6 小时,用户把 App 切到前台才重新计时。
  - `connectedDevice` 官方文档没写时长上限;它要求 manifest 里有 `FOREGROUND_SERVICE_CONNECTED_DEVICE`,再加 `CHANGE_WIFI_MULTICAST_STATE` 等几种权限中的一种,组播本来就要这个权限,正好满足。
  - 国产 ROM 杀后台的问题照实写进使用手册,不承诺后台一直能收。
- 保存:用 MediaStore 写到 `Download/gopan`;文件夹按相对路径还原。
- 系统分享菜单加一项「gopan 直传」(和现有分享入口并列),打开直传页选设备。
- 「存到网盘」:进现有的 `core/transfer/upload` 队列。

## 五、安全

- 监听端口就意味着局域网里谁都能连上来。陌生设备一定弹窗;可选设置一个 PIN(协议自带 `?pin=`,core 已经实现了失败次数限制)。
- 「我的设备」只认服务器给的指纹加 mTLS,设备名、IP 都不作数。
- 文件名一律清洗(core 的 `util/filename.rs`,再加上 doc/29 里 Windows 文件名的规则),拒绝 `..` 和绝对路径;接收前检查磁盘剩余空间是否够。
- 服务器上的 `lan_devices` 只返回给同一用户的其他有效会话;地址是内网地址,不进动态、不进日志。
- 「以后自动接收这台设备」记在本机,按指纹记;设置里能看到列表、能删。

### L1 · 桌面端和 LocalSend 互通

`lanshare`、`lan.rs`、直传小窗、接收弹窗、`lan_history`、存到网盘、右键「直传到…」、防火墙提示。不连服务器,所有设备都按陌生设备处理。

### L3 · 安卓

`.so` 和绑定、直传页、MulticastLock、前台接收、MediaStore 保存、系统分享入口、存到网盘。L3 发版后,桌面和安卓之间同账号免确认才算打通。

## 七、不做的

- **网页端**:浏览器发不了 UDP、也不能监听端口,只能走 WebRTC 加信令。跨网络还得自己搭 TURN 中转,最后又压回 VPS 的带宽上,不划算。
- **跨网络直传**(不在同一个局域网的 P2P):跨网络照旧走传输助手。
- **LocalSend v3**、反向传输(协议第 5 节:发送方开 HTTP,对方用浏览器下载)、web 分享页:等 v3 定稿、真有需求再说。
- **gopan 服务端自己当成 LocalSend 设备**(家里自建时「发到网盘」):收文件的一方没有人确认,做的话要另想鉴权,先不做。
- **和传输助手合并**(在传输助手里发文件时,对方就在附近就自动直传):直传的文件默认不进网盘,而传输助手的消息都指向网盘里的文件,两边语义不同。先各管各的,用一阵再看;以后可以在传输助手发大文件、对方又在附近时提示一句「直传更快」。
- **macOS / Linux 桌面端**:跟 doc/29 一样,先只做 Windows。
