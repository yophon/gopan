# 一行 FROM 叠出 75 层镜像：一个临时方案是怎么悄悄变成定时炸弹的

> 草稿。数字来自 2026-11-06 在生产机上的实测（`docker image inspect`、`docker history`）与仓库的提交记录；发布前核对标 `TODO(作者确认)` 的地方。

gopan 跑在一台 2 核 2G 的 VPS 上。某天顺手看了一眼镜像：

```text
$ docker images gopan
gopan   latest   c1ba9a27a037   2.6GB
```

一个 Go 二进制加 ffmpeg 的网盘，镜像 2.6GB。`docker images` 在 containerd 存储下会把压缩层和解开后的文件系统一起算，数字偏大；换 `docker image inspect` 看是 864MB，**75 层**。按完整的 Dockerfile 重新构建，只有 5 层。

这篇讲多出来的 70 层是怎么来的、为什么一直没人发现，以及怎么彻底修掉。

## 一、起因：一个合理的临时方案

2026-10-14，gopan 的部署遇到两个限制：

- **开发机上没有 Docker**，只有 Go 和 pnpm。
- **服务器只有 2G 内存，不能在上面构建**。前端 vite 加 Go 编译可能触发 OOM killer，把同机的博客、白板服务一起杀掉（doc/10 的部署复盘专门分析过这个风险）。

于是加了一条「无 Docker 开发机」的部署路径：本机交叉编译出 Linux 二进制，scp 到服务器，服务器上只做一次 COPY。Dockerfile 只有三行：

```dockerfile
ARG BASE=gopan:latest
FROM ${BASE}
COPY --chown=root:root --chmod=755 gopan-linux /usr/local/bin/gopan
```

`FROM gopan:latest` 是关键：运行时需要的东西（debian、poppler、静态 ffmpeg）都在上一次的镜像里，直接拿来当底，不用另外准备什么。一行搞定，机上零编译，几秒部署完。

代价当时就知道。部署文档里写着：

> 旧二进制那一层不会去掉，每次部署镜像涨 30 MB 左右。攒多了就按完整 Dockerfile 重建一次，交给 GitHub Actions。

**当时的判断是对的**：限制是真实的，方案改动最小，代价也写清楚了。

## 二、它是怎么失控的

### 1. 「攒多了重建一次」没有挂在任何会自动发生的事上

没有层数告警，没有体积检查，也不在部署流程里。重建这件事只存在于一段文档里，等着人想起来。

镜像其实重建过一次：10-21 上线内容搜索，运行层要加 poppler，就按完整 Dockerfile 重建了，栈从那天重新开始。但那次是新依赖逼出来的，不是因为「攒多了」。之后照旧按 prebuilt 部署。

部署的节奏也和设想完全不同。gopan 那段时间两周多发了 24 个版本。从 10-21 到 11-02，**12 天部署了 32 次**，用 `docker history` 把那 75 层逐层拆开：

| 层 | 层数 | 每层大小 |
|---|---|---|
| 10-21 重建出来的底（debian、apt、ffmpeg、当时的二进制） | 4 | 合计约 444 MB |
| 每次部署 COPY 的二进制 | 32 | 33～42 MB |
| 每次部署的 pdftotext 检查 `RUN` | 32 | 4.1 kB |
| 10-29 起每次部署的 qjs 检查 `RUN` | 7 | 第一次 2.6 MB，之后 4.1 kB |

### 2. 后面的改动在临时方案上继续打补丁

- 10-21 内容搜索要用 pdftotext：在 prebuilt 里加了一段 `RUN`，「老运行层没有 pdftotext 就装一下」。
- 10-29 服务器端跑助手要用 qjs：再加一段 `RUN`，「sha256 对不上就下载一份」。

两次补丁都让这个方案能继续用，但都没有回头问一句：底座是不是该改了？而且这两段检查**即使什么都不装，也各留下一层**（上表里那些 4.1 kB 的层），所以每次部署从叠一层变成了叠两层，10-29 之后变成三层。

### 3. 有一个硬上限，文档里没写

overlay 存储驱动的层数上限在 125 层左右，到了之后 `docker build` 直接失败。按每次部署叠三层的速度，再部署十几次就会撞上，照那段时间的节奏也就一个星期左右。它会在什么时候发生？就在你要上线一个修复的那一刻。`TODO(作者确认：上限的确切数字与报错信息，以 Docker 文档为准)`

## 三、修法：固定底座

问题的根源只有一处：**以上一次的成品为底**。改成以一个固定的运行层为底，每次只叠这一次的二进制。

### Dockerfile 拆出运行层

```dockerfile
FROM mwader/static-ffmpeg:7.1 AS ffmpeg

FROM debian:bookworm-slim AS runtime
RUN apt-get update && apt-get install -y --no-install-recommends ca-certificates curl poppler-utils poppler-data ...
RUN curl ... qjs ...
COPY --from=ffmpeg /ffmpeg /ffprobe /usr/local/bin/
USER gopan
HEALTHCHECK ...
ENTRYPOINT ["gopan"]

# 最终镜像:运行层 + 一层二进制
FROM runtime
COPY --from=build /out/gopan /usr/local/bin/gopan
```

### prebuilt 以固定的运行层为底

```dockerfile
ARG BASE=gopan-runtime:1
FROM ${BASE}
COPY --chown=root:root --chmod=755 gopan-linux /usr/local/bin/gopan
```

运行层在服务器上建一次：

```bash
docker build --target runtime -t gopan-runtime:1 .
```

这一步只有 apt 安装和拷贝，不编译。BuildKit 只构建目标阶段依赖的部分，前端和 Go 的构建阶段根本不会跑。2G 的机器上用了 **33 秒**。

系统依赖变了（加包、升 ffmpeg 或 qjs）时，把版本号加一（`gopan-runtime:2`）再建一次，一年也就几次。之前那两段补装的 `RUN` 也一起删掉了。

### 结果

| | 修之前 | 修之后 |
|---|---|---|
| 层数 | 75 | **5**，以后部署多少次都是 5 |
| 大小（`docker image inspect`） | 864 MB | **169 MB** |
| 每次部署新增 | 一层旧二进制，永远删不掉 | 替换一层二进制，旧的随旧镜像回收 |

新镜像的 5 层：

```text
41.8MB  COPY gopan-linux /usr/local/bin/gopan     ← 每次部署只换这一层
270MB   COPY /ffmpeg /ffprobe /usr/local/bin/
2.58MB  RUN curl ... qjs ...
55.6MB  RUN apt-get install ... poppler ...
85.3MB  debian:bookworm-slim
```

**为什么不是 1 层或 2 层？** 层数本身没有成本，问题从来不在「层多」，而在「层一直在涨」。下面 4 层是所有版本共用的运行层，不重复占磁盘，也不重复下载。硬压成一层反而失去缓存：以后只升级 qjs，也得把 apt 那部分一起重建。

切换生产的过程：用当前生产镜像里的同一个二进制（sha256 一致）按新写法构建，旧镜像先打上回滚标签，只重建 gopan 一个容器。**7 秒后健康检查通过**，Postgres 与 MinIO 没有重启。

CI 那条路顺带也改了：构建完整镜像时用 GitHub Actions 的构建缓存，依赖没变时运行层的层不变，服务器拉新版本只下载变化的那层二进制。

还有一点要老实说：切换之后磁盘使用率反而从 73% 涨到了 77%。新的运行层加了进来，而旧的那叠 75 层还被几个回滚镜像引用着。确认稳定之后把它们一起删掉，空间才会回收。

## 四、可以带走的东西

**1. 接受一个已知有代价的权衡时，给它挂一个会自动发生的检查，而不是写「记得定期做」。**

这次如果在部署命令前加一句「层数超过 40 就拒绝构建」，问题在 10-21 重建后的第一周就会暴露，而不是等到第 75 层。文档里的提醒只有在人去读的时候才起作用，而人在忙着发版的时候最不会去读。

**2. 给临时方案打补丁时，问一句「底座该不该改了」。**

pdftotext 和 qjs 那两次，都是解决眼前问题最小的改动。单独看都合理，叠在一起就把一个临时方案固化成了正式流程。

**3. 节奏一变，旧假设要重新算。**

「攒多了重建一次」默认的是一个月部署几次。12 天部署 32 次时，同一句话的含义完全变了。

最后说一句背景：gopan 是我一个人借助 AI 编码助手写的，当初那个 `FROM gopan:latest` 方案也是和 AI 一起做出来的。在当时那个任务里，它是最合理的答案：改动最小，代价写进了文档。问题出在确认这一环，没有人追问「这个代价什么时候会出问题」。这一环本来就该是人的工作。
